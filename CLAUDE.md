# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

TurboFieldfare is a Swift + Metal inference runtime for Gemma 4 26B-A4B (26B total, ~3.9B active) that runs on 8 GB Apple Silicon Macs. It keeps ~1.35 GB of shared weights plus an FP16 KV cache resident and streams the 8 routed experts each token needs from SSD.

## This repository

This repo is the **iOS port**, a separate repository derived from
[`drumih/turbo-fieldfare`](https://github.com/drumih/turbo-fieldfare) (Apache-2.0),
with upstream history kept and `upstream` wired fetch-only.

**Building the port and lowering bytes/token is the priority.** `docs/IOS_PORT.md`
is the active plan. `AGENTS.md` is the operator contract — it governs *how* to
work safely (model-process invariants, benchmark protocol), not what is in scope.

Much of `docs/` and all of `README.md` predate the port and describe the Mac
project. The table under [Document map](#document-map) says what each one is true
of; check it before trusting a document's framing or its numbers.

## The binding constraint

The binding constraint is inherited by the port and gets stricter there. ⚠️ **The reason given here until 2026-09-16 — that iOS has no page-cache tier to fall back on — was falsified by measurement on the iPhone 17.** iOS serves an app's reads from cache up to a knee between 1 and 4 GiB (see the device read-bandwidth row below). It binds harder on the phone for two other reasons: the 12.01 GiB routed-expert corpus sits far past that knee, and the device's uncached read rate of 1.650 GB/s on a freshly written corpus is below this Mac's like-for-like 2.30 GB/s. The binding constraint is **bytes read per token**, not compute. State the bytes/token effect first, then everything else.

Since 2026-08-10 that has a measured second half. Decode time is `bytes/token ÷ achieved fetch bandwidth`, and for part of that day the second factor was believed to hold the larger opportunity. **It does not.** Probing the installed layer files directly, later the same day, put a bare serial `pread` of the same blocks at 1.36 GB/s against the fetch path's in-situ 1.30–1.34 GB/s: the fetch path already achieves **94–96% of what these files deliver**, and queue depth, fd count, and planning cost are measured non-factors. Achieved bandwidth remains a legitimate axis to argue on — it is the second half of the identity, and a change can still make it *worse* — but the headroom is single-to-low-double digits, not the 2.2× the earlier arithmetic implied. Be precise about which baseline a proposal claims against: production is at **93–96%** of a bare QD1 serial read (1.40 GB/s on a quiet disk), **~90%** of a barrier-synchronized fan-out at its own average depth of ~2.6 misses/layer (~1.47), and **~72%** of the steady-state random ceiling (1.82 GB/s at QD4) — but that last pipeline is one the cb1/io/cb2 dependency cannot form, since `cb2` needs every expert of the layer before it can start. **That caveat is now closed, and the ranking did change (2026-08-11).** Every baseline in the sentence above is the rate of the *installed* files, and the rate of those files is not a property of the device — it is a property of **how they were written**. A sequentially written copy of the same bytes reads **1.29× faster at 0 h and 1.34× at 25 h** — a ratio that looked stable over that 25 h window, but was measured on synthetic `/tmp` controls and **did not hold on the production artifact at 7 d** (see the 2026-08-18 correction below) — and the installer writes the 30 layer files scattered (confirmed in code: `RangeCopyPlanner.coalesce` re-sorts every copy by `(shardID, sourceOffset)`). Queue depth is a second, independent multiplier worth **~1.17×** that stacks with it. So there was **one non-bytes lever on `io` with real room in it** — install-time write order, ~1.3× at 0 bytes/token, tracked as [IO-12](docs/experiments/summaries/01-model-install-and-expert-io.md#io-12). **It has since been spent, and then it evaporated.** The 30 installed layer files were rewritten sequentially on 2026-08-11 and the lever paid out end-to-end at +20.1% / +14.4% / +14.9% tok/s for a bytes/token delta of exactly zero — at the time the largest single win in this log, and the only one ever obtained without reading fewer bytes. **Re-measured on 2026-08-18, on the same artifact untouched for 7 d 16.8 h, that gain is gone: 3.271 / 2.858 / 2.674, i.e. −12.2% / −13.5% / −10.2% against the 0 h run and only +5.4% / −1.1% / +3.2% against the scattered artifact it replaced** — within noise of zero once the scattered baseline's ~3% Spotlight handicap is netted out. **Treat install-time write order as a transient effect, not a durable lever**, and do not quote the +20% figure as a standing gain. ⚠️ **Reopened 2026-09-15 — read [that section](#reopened-2026-09-15-8a33d02-the-second-rewrite-held-at-27-days) before relying on this paragraph:** a second rewrite, written on a 74%-full volume, still delivered 3.745 / 3.346 / 2.987 tok/s and 1.67–1.74 GB/s fetch at 26.8 d, so "transient" describes the first artifact, not the lever. What survives is a **standing invariant** (nothing may deliberately scatter the files) and an **open question**, not a product change: teaching the installer to write sequentially is only worth doing if the gain can be shown to persist, which it currently cannot. Outside of that, bytes/token is once more the only lever. A change proposed on fetch-path grounds still has to beat that bar, and the 4–6% figure below still applies to *the fetch path as it reads the artifact it is given*. Note also that a second term, **recency, is real but unquantified ([IO-13](docs/experiments/summaries/01-model-install-and-expert-io.md#io-13)) and is not claimable**: it applies equally to any two artifacts of the same age, so it cancels out of every comparison that matters and is only reachable by rewriting the model before each run, which is rejected on write amplification. What remains *not* interesting by default is lowering GPU time in a phase that is not on the critical path — which is a claim about a specific phase, and the `[phase-time …]` footer now settles it rather than leaving it to intuition.

Corollaries that follow from it, and that should shape proposals before compute ever enters the discussion: expert-cache hit rate is a first-class metric because a hit is a read that did not happen; routing locality across consecutive tokens is worth more than kernel throughput; quantization and layout changes matter mainly for how many bytes they pull per routed expert; prefill and decode have different byte profiles and must be reported separately.

**Established by measurement on 2026-08-10 and still true after the rewrite:**
the routed-expert fetch is the largest consumer of a decode forward on the 8 GB
host. Reads are where the time goes. But the margin has narrowed — `io` was
**59–63%** of a forward on the scattered artifact and is **54–57%** on the
rewritten one, because the lever compressed `io` and left everything else alone.

Two qualifications that any proposal has to respect. First, `io` is **at 94–96%
of the read rate its artifact can sustain**, so there is no bandwidth slack
waiting inside the fetch path. That was true of the scattered artifact and is
true of the rewritten one; what the rewrite changed is the artifact, not the
path. (The earlier claim here — that the fetch ran at "41–50% of the device's
bandwidth roof" and that closing the gap was "the largest known quality-free
win" — compared against a roof measured on zero-filled data and is **withdrawn**;
see [Measured facts](#measured-facts).) Second, GPU attention (`cb1-wait`) is
now **34–39% of a forward, up from 29–35%, and still rising with prompt
length** — not because it got slower (it did not; it fell slightly) but because
`io` shrank around it. **On the long case it is 129.7 ms against `io`'s 182.6,
and the two are converging.** It is not bytes, no lever in the port plan
addresses it, and on a long-context device workload it will matter; it is the
most likely place for the *next* win. The rule still ranks proposals, but a
change justified purely on bytes/token needs to say it is not making `cb1-wait`
worse, and one justified on bandwidth needs to say where the remaining 4–6% is
coming from — against the rewritten artifact's rate, not the old one.

### RETRACTED (2026-08-10, same day): "Why the 8 GB host is ~2.3× slower than a 16 GB host"

An earlier version of this section argued that our host runs at 95% of its SSD roof and that a 16 GB host's rate is unreachable from SSD, so ≥50% of its expert bytes must be served by the macOS unified buffer cache at DRAM speed. **The measurement below retracts the arithmetic on both sides.** The retracted text is preserved in git history at `d271628`; it is removed here rather than left standing because it was being quoted as settled.

What broke it: that argument used the **806.1 MB zero-hit ceiling as the demand figure**. Measured demand is 261.9 MB/token, because the 16-slot LFU cache hits 62–68% of requests. Redoing both sides with measured bytes:

- **Ours (8 GB):** 261.9 MB per 315.6 ms token = **0.83 GB/s, ~29% of the measured 2.7–3.2 GB/s SSD roof.** This host is *not* bound by the *device's* bandwidth ceiling during decode. (Two things here were later corrected. The "2.7–3.2 GB/s SSD roof" was itself measured on zero-filled data and is withdrawn; and the inference that ~230–280 ms of each token therefore goes somewhere other than expert bytes was wrong — only ~120 ms does. See the resolution below.)
- **16 GB M1 Air (7.802 tok/s, issue #76):** identical token counts, so identical routing and — by the same-policy argument — the same hit rate and the same 261.9 MB/token. That needs **2.04 GB/s**, which this retraction called "inside the SSD roof". ⚠️ **That half of the retraction was itself wrong, and is corrected below:** 2.04 GB/s is *outside* the real roof — above both 1.36–1.39 GB/s random and 1.71 GB/s sequential on real data. It only looked reachable because the roof it was compared against had been measured on zero-filled data.

### RESOLVED (2026-08-10, `ce287b6`): decode is expert-read-bound, and the fetch path is at the roof these files allow

The phase split above was taken and it answers the question the retraction left open. **`io` is 59–63% of a decode forward** — the largest consumer by a wide margin, roughly twice the next one. The binding constraint holds on this host: bytes/token is where the time goes, and the "operating assumption" caveat in [The binding constraint](#the-binding-constraint) is discharged for the Mac host.

`io` moves those bytes at **1.30–1.34 GB/s**. For part of 2026-08-10 that was read as "41–50% of the device roof", i.e. a 2.2× quality-free win sitting in the fetch path. **A direct probe of the installed layer files closed that question the same day: there is no such win.**

- A bare serial `pread` of the *same files*, at the same block size, with no runtime around it, achieves **1.36 GB/s** (2,472 µs/read, 300 reads, 12.01 GiB working set). Production gets 1.30–1.34. The fetch path is at **94–96% of achievable**.
- The 2.7–3.2 GB/s "roof" was an artifact of the probe file's *contents*. On a fresh 6 GiB file at identical fragmentation, zero fill reads at 2.36 GB/s and incompressible data at 0.77 GB/s — 3.1× apart on content alone. Zeros never pay full NAND cost; INT4 expert weights are incompressible (IO-07).
- Everything proposed as the cause is measured and ruled out: **queue depth** (k=2/3/8 aggregate 1.43–1.55 GB/s vs. 1.36 serial — flat), **30 fds vs. one**, and **planning cost**, which the code places outside the `io` timer.
- **Fragmentation is real but second-order.** Every production read spans 4.30–8.62 discontiguous extents, yet 2.3× more extents/read costs only ~11% latency. Perfect locality is worth ~1.26× (1.71 GB/s sequential vs. 1.39 random) and routing cannot deliver it. A file written today lands at 18 extents/read — *worse* than the installed artifact — so CACHE-09 preallocation would now backfire.

The earlier bullet concluded that 230–280 ms/token had to be going somewhere other than expert bytes. It is not: only ~120 ms is, and that inference stays withdrawn.

**The 2.3× gap vs. the 16 GB M1 Air now has a supported explanation, not just a candidate.** That host completes a whole forward in ~128 ms while ours spends ~202 ms in `io` alone; at the same 261.9 MB/token it would need **2.04 GB/s, which exceeds both the 1.39 GB/s random and the 1.71 GB/s sequential real-data rates measured here.** On an SSD equal to ours it therefore *cannot* source all its expert bytes from storage — at least ~32% must come from the page cache, which its extra ~8 GB of RAM can plausibly hold against the 12.01 GiB corpus. This restores, with corrected demand arithmetic, the conclusion the retraction above withdrew. It still rests on one assumption that has never been measured: **that the 16 GB host's SSD roof equals ours.** ⚠️ **Amended 2026-08-11:** our `io` is now ~152 ms, not ~202, and our fetch reaches 1.72 GB/s, so the headroom this argument leans on is smaller than when it was written. It survives, because the 16 GB host ran the *same installer* and therefore holds a scattered artifact too — 2.04 GB/s is still out of reach for one — but the margin is now ~1.2× rather than ~1.5×, and a 16 GB host that rewrote its files sequentially could plausibly close it from storage alone. **This is a second untested assumption stacked on the first; treat the page-cache explanation as weaker than it was.**

Second finding, unrelated to bytes: **`cb1-wait` is 95–133 ms per forward (29–35%) and grows with prompt length** — GPU attention and router over a lengthening KV cache. It is the second-largest consumer, it is compute rather than I/O, and no lever in the port plan currently addresses it.

**Consequence for the port, revised twice:** 16 GB+ community numbers *are* partly a page-cache measurement — the corrected arithmetic above supports it, subject to the equal-SSD assumption. That does not rescue decode, since the routed-expert corpus is 12.01 GiB, but the tier is not absent and arguments must stop assuming it is. Caveats that still stand: the 16 GB host's SSD roof is assumed equal to ours, not measured; community rows are single runs.

**And the practical consequence for optimization work:** `io` is the largest phase *and* within 4–6% of its achievable rate, so the only way to take time out of the fetch path is to read fewer bytes — hit rate, routing locality, or bytes per routed expert. Proposals to make the fetch path itself faster (deeper queues, an I/O thread pool, read reordering, preallocation) are arguing over ~4–6%, on top of IO-04, IO-05, and CACHE-07 having each already failed to find it. **The one exception found — changing the artifact rather than the path — is recorded below and is now spent.**

And [IO-13](docs/experiments/summaries/01-model-install-and-expert-io.md#io-13) is now the more important open question, not the footnote it was filed as.

### OPEN (2026-08-19, `c85ce98`): production saturates near 1.7–1.8 GB/s, and "94–96% of achievable" no longer holds

## Architecture

### Module graph

`TurboFieldfareFormat` (Foundation-only, no Metal) owns the `.gturbo` v1 wire contract — manifest, packed-experts layout, resident index — and is shared by the installer, the verifier, and the runtime so all three validate identically. `TurboFieldfare` is the runtime library (Metal kernels + inference); everything else depends on it.

Every executable is split into a testable `…Core` library target and a thin `…/Command` executable target (`TurboFieldfareRepackCore`, `TurboFieldfareCLICore`, `TurboFieldfareServerCore`, `TurboFieldfareAppCore`). Put logic in the Core target; the executable target should only parse arguments and call in. `TurboFieldfareValidationSupport` holds CPU reference implementations, PRNG, and tolerances used by kernel tests.

The Mac app is two processes: `TurboFieldfareMac` (SwiftUI/AppKit UI, `AppCore` + `MacPresentation`) talks over a Unix socket to a one-shot `TurboFieldfareDecodeService` that solely owns the model and Metal. Codable messages live in `TurboFieldfareDecodeProtocol`. The UI process never loads a second in-process model, which is why the HUD reports *decode-service* memory rather than its own.

### The bounded-memory rule

No install, load, test, or benchmark path may put a whole model, shard, expert, or source tensor into Swift heap memory. Concretely: the installer streams pinned Hugging Face byte ranges straight into `.gturbo` layout through tile-sized scratch (validated max 512 KiB payload and scratch), `model_weights.bin` is mmapped read-only and wrapped in `MTLBuffer`s without copying, and routed experts land in pre-allocated 2 MiB-aligned slot buffers via `makeBuffer(bytesNoCopy:)` + `pread`. Any change that buffers a full tensor breaks the project's core premise.

### Decode: the cb1 / io / cb2 handoff

Per layer, `cb1` (Metal) runs norm → QKV → RoPE + KV write → attention → output projection → router, stopping when the top-8 expert IDs are readable by the CPU. `io` plans against the layer's 16-slot LFU cache and `pread`s only the misses, while Metal runs the resident shared-expert branch concurrently. `cb2` finishes the routed branch, reduces by router weights, combines with the shared branch, and applies the layer tail.

The phases run in sequence within a layer; `DecodePhaseTimings` carries the six figures the CLI's `[phase-time …]` footer prints, and they account for ~98% of a forward's wall time. Two scope traps: `cb1`/`cb2` are CPU encode cost with GPU execution excluded (that execution is the separate `cb1-wait` and `routed-drain` figures), and `io` is a window during which the shared-expert branch is executing on the GPU, so it is not idle time.

Prefill is layer-major in chunks of ≤128 tokens, streams experts in tiles of ≤8 (two tiles must fit the 16-slot cache), and uses staged-affine MPP `matmul2d` for projections with enough rows; single-token decode stays on custom affine INT4/INT8 GEMV kernels.

### Metal

`.metal` sources under `Sources/TurboFieldfare/Metal/` are copied as bundle resources and compiled into one `MTLLibrary` at startup by `MetalContext` (single owner of device, queue, library, and a lock-guarded pipeline cache) — edit a shader, rebuild the Swift target, no Xcode metallib step. Swift-side kernel wrappers live in `Sources/TurboFieldfare/Kernels/`, mirroring the `Metal/` subdirectories.

Load-width gotcha: packed-weight load width must match the alignment the path actually guarantees. Resident INT4 GEMVs and routed gate/up projections build 4-byte values from two `ushort` loads because offsets can be only 2-byte aligned; routed down-projection offsets are 4-byte aligned and may use `uint` loads.

### Invariants worth knowing before editing

- A queued GPU consumer owns its expert slot and scratch bank until completion; CPU reuse must not race an earlier command buffer.
- K and V stay distinct after normalization/RoPE even where the raw projection is shared (full-attention layers derive both from raw K; K gets scaled per-head norm + RoPE, V gets no-scale norm and no RoPE).
- The repacker relayouts quantized values byte-for-byte; it never dequantizes and requantizes.
- Kernels may reorder float ops but must stay deterministic within a path and inside `Tolerances` — exact identity across paths is not required.
- Gemma 4 specifics the runtime must match: NeoX RoPE, attention scale `1.0`, no router-logit softcap, parallel shared + routed FFN, learned layer scalar, final logit softcap `30.0`, tied 4-bit embedding/head.

`docs/SYSTEM_DESIGN.md` has the full picture and a code map to the entry-point files; `docs/RUNTIME_CONTROLS.md` is the authoritative list of exposed controls and defaults.

## Conventions

- Tests use swift-testing (`@Suite` / `@Test`), never XCTest. Shared Metal state makes in-process parallelism unreliable, so always go through `Scripts/test.sh`; add `.serialized` to suites that touch process-wide state. Kernel tests compare against the CPU reference in `TurboFieldfareValidationSupport` with a seeded `SplitMix64` and named tolerances.
- `docs/RUNTIME_CONTROLS.md` documents the controls the Mac runtime exposes; production defaults are 8K context for the CLI and app and 16K for the server (4K before the 2026-09-15 upstream merge; the benchmark protocol passes `--max-context 4096` explicitly, so measured rows are unaffected), **16 expert-cache slots on macOS and 32 on iOS** (`RuntimeConfiguration.productionExpertCacheSlots`; slots are per layer, so that difference is +1.61 GB, and 32 is harmful on the 8 GB Mac but worth +34–59% on the iPhone 17), LFU, prefill on with 128-token chunks, RDADVISE off, temperature `0.2` / Top-K `64` / Top-P `0.95`. The port will add controls (cache sizing against the memory ceiling, jetsam policy) — add them there rather than treating the current list as closed.
- Currently macOS 26 / Swift 6.2 / Metal 4, arm64 only; Swift 6 language mode. iOS platforms get added by the port; keep the macOS build working, since it is the reference the port is validated against.
- Behavior changes need a focused test. Keep PRs narrow — good practice here, and it keeps individual changes cherry-pickable back to upstream. Report commit, hardware/RAM, macOS, Swift version, exact command, exit code, and the full timing footer or error for any real-model run.
- The server has no auth or TLS: keep it on `127.0.0.1`, never proxy or tunnel it, and let the client authorize every model-produced tool call.

## Working agreements

These are rules for how work gets done here, not style preferences.

### Every optimization states a predicted bytes/token delta first

Before implementing any change proposed as an optimization, write down:

1. **Predicted bytes/token delta** — a signed number or a tight range (e.g. `−180 KB/tok`, `0 ± 5%`), not "should reduce reads".
2. **The mechanism** — which reads disappear, get coalesced, get cached, or get deferred.
3. **What would falsify it** — the measurement that would show the prediction was wrong.

No prediction, no implementation. A change predicted at zero bytes/token delta is allowed, but must be labeled as such up front and justified on other grounds. Those grounds are: **achieved fetch bandwidth or another named phase in the `[phase-time …]` split** (state which phase and a predicted ms/forward delta, held to the same standard as a bytes/token one — a signed number and a falsifier), correctness, the memory ceiling, or portability to iOS. Nothing else. "Cleaner" is not a ground. After implementation, record the measured delta against the prediction in `MEASUREMENTS.md` — including when the prediction missed. Wrong predictions kept honestly are the point; silently dropping the ones that missed destroys the record's value.

### Use a subagent for codebase search

Do not glob, `find`, or ripgrep the tree into the main context to answer "where is X". Dispatch the `codebase-search` subagent (`.claude/agents/codebase-search.md`) and work from the file paths and line ranges it returns, reading only the specific regions you actually need. The main context is reserved for the code under active discussion and the measured facts above — bulk search output crowds both out.

Direct search is fine when you already know the exact file and are confirming one symbol in it.

### Use plan mode before editing any `.metal` file

Shader edits land in a single `MTLLibrary` compiled at startup, are validated only against the CPU reference in `TurboFieldfareValidationSupport`, and carry the load-width and alignment hazards described above. Enter plan mode, state the change and its bytes/token delta, and get agreement before touching anything under `Sources/TurboFieldfare/Metal/`. Swift-side kernel wrappers in `Sources/TurboFieldfare/Kernels/` do not require plan mode, but a wrapper change that alters dispatch shape or buffer layout should be treated as if it did.

### Persistent memory across sessions

Sessions do not share context; these files do. Read them before proposing work, and write to them when a session produces a durable result:

- `MEASUREMENTS.md` — append-only run log. Every real-model run gets a row. Never edit or delete an existing row.
- `docs/experiments/summaries/` — what has already been tried *in this project*, what it measured, and why it was kept or abandoned. This is the source of truth for in-project prior art; read the file for the phase you are touching (map below) before proposing an optimization. A rejected idea needs a new argument, not a repeat. Do not re-summarize these into a new document.
- `docs/EXTERNAL_PRIOR_ART.md` — techniques from outside the project (papers, other runtimes, vendor docs) with an assessment of whether they apply under the bytes/token constraint.

If a session's conclusion is not written into one of these, it did not happen.
