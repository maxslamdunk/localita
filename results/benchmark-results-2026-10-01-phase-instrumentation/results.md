# Results: GPU execution time and per-read latency in the decode footers

Scored against [`predictions.md`](predictions.md), committed first in
`4b90254`. The change is `72a7312`.

## What was run

An A/B smoke on the 8 GB M1 validation host, **not a benchmark row**: the
`short-explanation` case of `real-generation-v1` with its seed (20260721) and
sampling defaults, but `--max-new 64` instead of 1024, so 63 decode forwards per
run. Mac default 16 slots, 4K context. Baseline is `e46b8d1` built in the same
worktree; treatment is `72a7312`. Ten runs in fresh processes, interleaved
base, new, base, new, then new, base, base, new, new, base, so neither binary
always ran second. AC power; **Spotlight indexing on and the volume 92% full
(16 GiB free)**, both of which add storage noise. Scripts and every stderr
footer are in [`logs/`](logs/).

## Scoring

**P1, identical work: held.** All ten runs generated byte-identical text
(one SHA-256 across ten stdout files). bytes/tok 264.13 MiB, hit rate 65.6%,
req/tok 240.00 and reads/tok 82.46 matched to the digit in every run.

**P2, no measurable cost: not falsified, and not tested at the 1% it
claims.** Wall ms/forward:

| | runs | median |
| --- | --- | --- |
| baseline | 287.53, 289.83, 302.13, 311.54, 315.72 | 302.13 |
| new | 287.11, 302.16, 314.52, 317.53, 370.15 | 314.52 |

The baseline's own spread is 9.8%, the fastest single run was a new one, and a
rank test on these ten runs is far from significant (U = 8, critical 2 at
n = 5 + 5). One new run (370.15) is an outlier, with `io` at 241 ms against
172–199 for the other nine; `cb1-wait` moved with it (99.6 against 88.6–92.3),
which no instrumentation cost would cause. The mechanism argument stands: about
a hundred property reads per forward and two clock reads plus an uncontended
lock per 3.36 MB read. But this host's noise today cannot resolve ±1%, so P2
is supported only at about the 10% level.

**P3, internal consistency: held.** In all five new runs:
- the attention + router buffer (41.75–47.15 ms) is below `cb1-wait`
  (88.60–99.59);
- `busy` (120.15–134.43) is below `wall` (287.11–370.15);
- the histogram holds exactly 5,195 decode reads, which is reads/tok × forwards
  (82.46 × 63).

The head buffer's GPU time (14.73–15.68 ms) also sits just under the head's
wall-inclusive timer (15.01–15.95).

**P4, expert GPU work 30–50 ms/forward: held at the falsifier.** Cache-hit plus
routed buffers 45.09–52.43 ms, inside the 20–60 falsifier band. Four of five
runs are inside the 30–50 point range; the outlier run is just above it.

**P5, `idle` at 50–95% of `io`: falsifier fired.** Measured 97–98% in every
run. The prediction was specified against the wrong quantity: `idle` is all
GPU idle time in the forward, including time outside `io` (CPU encode,
sampling, untimed gaps), so it can approach or exceed `io`. A derived estimate
of GPU idle *within* `io` is `io` minus the shared and cache-hit buffers that
run in it: (183.55 − 25.59 − 14.46) / 183.55 = **78%** on run new2. That
assumes both buffers fall wholly inside `io`, which nothing measured here
establishes.

**P6, under 10% of decode reads below 0.5 ms: held; the predicted mode
missed.** 0.0% of decode reads and 0.0% of prefill reads were under 0.5 ms in
every run, so on this host the OS file cache served essentially none of the
misses. But the mode was **4–8 ms** (34–54% of reads), with 8–16 ms at
30.5–51%, not the predicted 1–2 or 2–4 ms. The cause is in the code read before
predicting: `executeExpertCachePlan` issues a layer's misses concurrently
through `concurrentPerform`, about 2.75 at a time at 16 slots, and each read's
own duration stretches with the others in flight. Mean 7.00–9.41 ms per decode
read against 1.91–2.01 ms per prefill read.

## What the new lines show

All on one host, one case, 63 forwards per run; read them as a first
measurement, not a fact table row.

1. **`cb1-wait` is half attention and router.** The attention + router buffer
   is **47–48%** of `cb1-wait` in every run. The previous layer's routed buffer
   (29 of 30 per forward land in the next layer's wait) is another 30.3–35.6
   ms. The remaining **16–17 ms per forward (17–19% of `cb1-wait`, about
   0.54 ms per layer)** is covered by neither buffer's GPU execution. That is
   CPU/GPU handoff latency inside the wait. The earlier estimate of 1–5 ms per
   token for the per-layer round trip was about three times too low.
2. **The GPU is busy for 36–42% of a forward.** It is idle 167–236 ms of
   287–370.
3. **The shared expert costs 24.3–25.6 ms/forward of GPU time**, all of it
   scheduled during `io`.
4. **Concurrent decode reads buy no throughput here.** `io` divided by reads is
   2.09–2.92 ms per read, against 1.91–2.01 ms for a prefill read. That agrees
   with the queue-depth results already on record for this host; it is not a
   new finding.

The iPhone has not been run with these lines yet. Its file-cache share is the
question P6 deliberately made no prediction for.
